# Тесты (pytest)

Конфигурация — `pyproject.toml`: `asyncio_mode = "auto"`, `testpaths = ["tests"]`, маркер `integration`.
В проекте тесты — обычные функции `test_*` (без классов, Allure и BaseTest). Эту форму сохраняем;
классы допустимы только для группировки близких кейсов, когда это реально упрощает чтение.

- `tests/unit/` — быстрые, без сети, БД и Redis; зависимости заменяются `AsyncMock`/`MagicMock`.
  `tests/integration/` — помечены `@pytest.mark.integration`, при отсутствии Postgres/Redis делают `pytest.skip`.
- Файл называется по тестируемому модулю: `tests/unit/test_<module>.py`; имя теста описывает поведение
  (`test_cancel_raises_when_order_not_open`).
- Структура Arrange–Act–Assert; один тест проверяет одно поведение.
- Общие фабрики и хелперы — в `tests/fixtures/` или `conftest.py`; не копировать `_service()`/`_order()` из файла в файл
  (на третьем дубле выносить). Данные создавать фабриками, а не повторять литералы по тестам.
- Никаких реальных запросов к Telegram и OpenAI; время и случайность делать детерминированными (передавать `now`, не `sleep`).
- Тесты независимы: без общего изменяемого состояния и порядка выполнения.
- Новая фича и исправленный баг получают тест; сначала красный тест, потом код (см. `/tdd`).
- Цель — осмысленные проверки бизнес-логики, а не процент покрытия; `pytest-cov` использовать для поиска
  непокрытых веток в изменённом коде.
- Справочник: skill `python-testing` (при расхождении приоритет у этого файла).
